## Summary

Create a repo-local `documentation/` tree with an `open-source-contributing/` subdirectory containing markdown guides adapted from [opensource.guide](https://opensource.guide/) — covering how-to-contribute, finding projects, communication norms, maintainer-side guides, code of conduct, legal, getting-paid, and related topics. Source content is CC-BY-4.0 ([opensource.guide license](https://github.com/github/opensource.guide/blob/main/LICENSE)); guides will be adapted (not verbatim-copied), tailored to this practice's specialty (permissions/access/identity per [FEAT-0004](FEAT-0004.md)), and each file will carry the required CC-BY-4.0 attribution boilerplate.

## Target Audience

Two primary readers:

1. **Future AI sessions / collaborators** working on contributions out of this repo — guides serve as the procedural handbook for "how this practice contributes to upstreams."
2. **Curious visitors to the repo** who want to understand how we work without reading every task file. The guides answer "how do you decide what to contribute," "how do you do disclosure," "how do you handle attribution," etc. — at a level above the per-task implementation detail.

A tertiary audience is **prospective contributors to this repo itself** if the project ever invites outside contribution. The guides should be useful for that case without being primarily written for it.

## Implementation Notes

- **License compliance first, content second.** Do not draft any adapted guide content until `LICENSE-ATTRIBUTION.md` and the per-file footer template are in place. Easier to write to a known attribution standard than to retrofit attribution onto written content.
- **Adapt, don't copy.** CC-BY-4.0 permits verbatim copy with attribution, but adaptation is the goal here regardless. Verbatim copy would also import opensource.guide's voice, which doesn't match this repo's. Use opensource.guide's *structure* and *topic coverage* as scaffolding; write the prose in this repo's voice.
- **Defer the directory-name bikeshed.** Pick `documentation/` (matches the instruction verbatim) unless there's a specific reason to deviate. If you go with `docs/`, document the deviation in the implementation task's notes.
- **MVP scope.** First implementation pass writes 5-7 guides, not all 8+. The rest are listed as future in `documentation/README.md`. Better to ship 6 solid guides than 11 stub guides.
- **Do not invent a repo-root LICENSE.** If the repo doesn't already have a LICENSE file, surface that as an open question to the user — picking a license for the whole repo is out of scope for this task. The CC-BY-4.0 attribution on the adapted guides covers only those files; the broader repo licensing decision is separate.
- **Coordinate with FEAT-0004 if it lands first.** If FEAT-0004's PLAN.md ships before this task starts implementation, several of the guides (notably `finding-projects.md`, `how-we-contribute.md`) can pull their substantive content from the approved strategy. If FEAT-0004 hasn't landed, write the guides parameterized over the contribution-mode menu (with TODO markers pointing to FEAT-0004's eventual decisions).
