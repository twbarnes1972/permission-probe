# GTSK-0003: Research paid bug bounty programs — aggregators + per-project for our contribution portfolio

**Created:** 2026-05-18
**Status:** Open
**Priority:** Medium
**Category:** General Task

---

## Summary

Produce a research report cataloging paid bug bounty programs relevant to this practice's specialty (permissions, access control, identity). Two layers: (1) the major **aggregator platforms** that host most public programs, and (2) **per-project programs** for each open-source project in [FEAT-0004](FEAT-0004.md)'s initial candidate list. For each program, capture scope (does it cover permissions/identity?), payout structure, response SLA, prior-disclosure policy, and any conditions that would disqualify the kind of work this practice does (e.g., "no public disclosure before X days"). Deliverable is a markdown report under `tasks/working_artifacts/GTSK-0003/` that feeds FEAT-0004's project-prioritization rubric and informs FEAT-0003's per-project disclosure-channel planning.

This task is **research**, not contribution. No submissions, no engagement with programs, no outreach.

## Acceptance Criteria

- [ ] **Aggregator survey.** One section per major platform with the following fields per platform: URL, business model (paid vs VDP-only vs hybrid), program-discovery surface (public directory? invite-only? both?), how a researcher signs up, our practice's posture toward the platform (would we participate? under what conditions?). Initial list to cover:
  - [ ] [HackerOne](https://www.hackerone.com/) — largest, hosts Anthropic VDP (GTSK-0002 cross-ref) and many enterprise programs.
  - [ ] [Bugcrowd](https://www.bugcrowd.com/) — second-largest, comparable feature set.
  - [ ] [Intigriti](https://www.intigriti.com/) — Europe-focused.
  - [ ] [YesWeHack](https://www.yeswehack.com/) — Europe/APAC, growing public program list.
  - [ ] [Synack](https://www.synack.com/) — invite-only, vetted-researcher model; note as out-of-scope for an early-stage practice but worth knowing.
  - [ ] [Internet Bug Bounty (IBB)](https://hackerone.com/ibb) — hosted on HackerOne; pays for vulns in widely-used open-source libraries; **highly relevant** because several FEAT-0004 candidate projects (Python, PostgreSQL, OpenSSL/related crypto) are in IBB's scope.
  - [ ] [GitHub Security Advisories + GitHub Bug Bounty](https://bounty.github.com/) — first-party GitHub program; relevant where contribution targets are hosted on GitHub.
  - [ ] [Open Source Security Foundation (OpenSSF) Alpha-Omega](https://openssf.org/community/alpha-omega/) — not exactly a bounty but a funding source for security work on critical open-source projects; flag as adjacent.
  - For each aggregator: note whether it imposes a "no public disclosure" window that would conflict with FEAT-0003's responsible-disclosure default (typical: 90 days). Flag conflicts explicitly.
- [ ] **Per-project program lookup for FEAT-0004's initial 12-project list.** For each of Python, Traefik, PostgreSQL, Windmill, Supabase, Restic, Kafka, Pomerium, CoreDNS, FreeRADIUS, Apache Airflow, Firezone:
  - [ ] Does the project (or its primary sponsor / hosting foundation) run a paid bug bounty program? Where?
  - [ ] If yes: scope coverage (permissions/identity in scope?), payout range, response SLA, eligibility constraints, disclosure terms.
  - [ ] If no formal program: does the project have a security policy (`SECURITY.md`)? A vulnerability-disclosure email? A coordinated-disclosure preference? Capture the channel even when there's no money.
  - [ ] Note any sponsor relationships that matter: e.g., Apache projects → Apache Software Foundation security policy; PostgreSQL → core team security@; Kafka → ASF; Python → PSF + IBB. Project-level absence of a bounty doesn't mean no path to payment if a sponsor program covers it.
- [ ] **Permissions/identity scope filter.** The report's *summary table* explicitly flags which programs would pay for the kind of work this practice does — i.e., findings in permission matchers, access control bypasses, identity/auth flaws, RBAC misimplementations. Some programs are broad (any vuln); some are narrow (e.g., only ACE in specific listed products). The summary surfaces this so the prioritization rubric in FEAT-0004 can use it.
- [ ] **Disclosure-policy compatibility check.** Cross-reference each program's disclosure terms against FEAT-0003's charter posture (responsible disclosure, default-public-after-fix, conflict-of-interest disclosure on every report). Flag any program with terms that would conflict — e.g., perpetual-NDA programs, programs that forbid public writeups even post-fix, programs that require exclusivity (no parallel upstream-issue commentary). Those flags become eligibility constraints in FEAT-0004's rubric.
- [ ] **Honest viability assessment.** For each program with a payout: rough sense of whether a finding of the shape we produce (binary-disassembly-backed root cause + reproducer + suggested fix) is the kind they pay well for, vs the kind they triage-and-dismiss. Be candid — many bug bounty programs are tuned to expect web-app findings (XSS, IDOR, auth bypass over HTTP) and may underpay or misroute deep-system findings. This is an honest market read, not a sales pitch.
- [ ] **Aggregator-of-aggregators check.** Is there a current authoritative directory of bug bounty programs (e.g., [disclose.io](https://disclose.io/), [bugcrowd.com/list-of-bug-bounty-programs](https://www.bugcrowd.com/bug-bounty-list/), [chaos.projectdiscovery.io](https://chaos.projectdiscovery.io/))? Note them as references the report cites rather than reproducing entire lists.
- [ ] **Refresh cadence + ownership.** Bug bounty program scopes change frequently — payouts get adjusted, scopes expand/contract, programs end or are launched. Define how often this report gets refreshed (suggested: quarterly, or whenever FEAT-0004 considers adding a new project to the portfolio) and where the refresh task lives (probably a recurring GTSK opened from the cadence cycle).
- [ ] **Output format.** Single markdown file at `tasks/working_artifacts/GTSK-0003/bounty-programs.md` with: top section = summary table (program → operator → permissions-scope-yes/no → payout range → disclosure-compatibility-flag), then a per-program detail section, then a per-FEAT-0004-project section. If the report gets too long for one file, split per-project details into sibling files under the same folder per [tasks/artifacts_convention.md](../artifacts_convention.md).

## Implementation Notes

- **Research task, not action task.** No submissions, no outreach. The report is reference material for downstream decisions (FEAT-0004 prioritization, FEAT-0003 channel planning, future GTSK tasks that actually submit findings).
- **Citations required.** Every claim about a program's scope or payout cites the program's policy URL (preferably with a date of access, since these change). Don't paraphrase from memory.
- **Avoid copying long-form policy text.** Link to it; quote only what's load-bearing for the report's analysis. Some program policies have their own license terms — links are safer than embedded prose.
- **Be candid about uncertainty.** For programs with vague public scope, or projects where the security policy is "email this address," the report says so rather than fabricating clarity. Open questions are an acceptable output.
- **Cross-link GTSK-0002.** The Anthropic VDP entry under HackerOne is already being acted on in GTSK-0002 — the report's HackerOne section notes this and points to GTSK-0002 rather than re-analyzing Anthropic's terms.
- **Web research will dominate.** This task is mostly `WebFetch`/`WebSearch` against program pages, security policies, and disclose.io-style directories. Stay in the research mode — do not start drafting submissions.
