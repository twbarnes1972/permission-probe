# FEAT-0002: Build (and maintain) deep expertise in Claude permissions + security — knowledge base, change-tracking, verification suite

**Created:** 2026-05-18
**Status:** In Progress
**Priority:** Medium
**Category:** Feature

---

## Summary

Plan (not yet build) a durable workflow for becoming — and staying — expert in Claude Code's permissions and security model: the matcher, the hook system, `settings.json` schema and inheritance, sandbox/bypass modes, MCP auth and trust boundaries, the Skill permission surface, and how all of these change release-over-release. Deliverable of this task is a written plan covering a knowledge-base structure, update-tracking workflow, regression-verification approach (extending `probe.js`), and a learning roadmap. Implementation of any piece is downstream and gated on plan approval.

This is broader than [FEAT-0001](FEAT-0001.md) — that task is about triaging specific upstream GitHub issues; this one is about building the underlying *domain* expertise that makes triage (and root-cause work like [ISSUE-0001](../closed/ISSUE-0001.md)) cheap and authoritative.

## User Story

As the maintainer of `permission-probe` — which only exists because of one disassembly-deep root-cause investigation — I want a structured way to deepen and refresh expertise in Claude Code's permission and security architecture, so that:

- The expertise compounds rather than rotting between investigations.
- When a new Claude Code release changes the matcher / hook system / settings schema, I notice within days (not when a user complains months later).
- I can answer permission questions authoritatively with citations to source-of-truth artifacts (binary offsets, version-pinned probe results, official docs), not hand-wavy recall.
- The knowledge is portable enough that a future AI session in this repo (or a future me) can pick it up without re-deriving from scratch.

## Background

[ISSUE-0001](../closed/ISSUE-0001.md) showed the value of going deep — disassembly of `claude.exe` 2.1.143.a06 yielded two distinct root causes, a working hook, and three substantive upstream comments. But:

- That depth came from one focused investigation. Without active maintenance, knowledge rots: the next claude.exe release re-minifies, re-orders, and possibly re-architects the matcher. Cached offset numbers go stale immediately.
- "Permissions and security" extends well past the `XIq` matcher: hook lifecycle (PreToolUse/PostToolUse/Notification/SubagentStop/etc.), `settings.json` cascade (system → project → user → local), `permissions.allow`/`deny`/`ask`, `additionalDirectories`, sandbox + bypass modes, MCP server trust boundaries, Skill permissions, the cwd scope guard, filesystem ACL interaction. We have detailed knowledge of *some* of this and shallow-or-no knowledge of the rest.
- The system is a moving target. Anthropic ships frequently. Each release potentially shifts the threat model and the workaround landscape.

The cost of *not* doing this: every future investigation re-pays the same ramp-up cost ISSUE-0001 paid. The cost of doing it: planning effort now + ongoing per-cycle effort (probably small if done right).

## Acceptance Criteria

- [ ] **Topic scope definition.** Concrete list of what's "in scope" for Claude permissions + security expertise. Suggested starter: permission matcher (`XIq`, `v$_`/`xX8`/`JIq`, per-tool `checkPermissions`), hook system (all lifecycle events, payload formats, sandbox boundaries), `settings.json` schema (cascade, scope of each field, undocumented keys), permission modes (`default`, `acceptEdits`, `bypassPermissions`, `dontAsk`, `plan`), sandbox + bypass gating, `additionalDirectories` and cwd scope check, MCP server trust model + auth, Skill permission surface, Bash/PowerShell content matchers, filesystem-ACL interaction. Note explicit *out* of scope (e.g., model behavior, prompt-injection defense — different domain).
- [ ] **Knowledge base structure + storage.** Pick a format and location: markdown KB in `tasks/working_artifacts/FEAT-0002/kb/`, a `docs/permissions/` tree in this repo, the cross-session memory system, a separate repo, or external (Notion/Obsidian). Each topic page needs: summary, source citations (binary offsets / docs URLs / GitHub issue numbers / release versions verified against), known unknowns, last-verified date. Justify the format pick.
- [ ] **Authoritative sources catalog.** Curated list with brief annotations: official Anthropic docs URLs (claude.com/claude-code surface), `claude-code-guide` subagent (when to invoke), the embedded JS bundle in `claude.exe` (with disassembly methodology pointer), this repo's own [INVESTIGATION.md](../working_artifacts/ISSUE-0001/INVESTIGATION.md), relevant upstream issues, useful third-party writeups. Distinguish primary (binary/docs) from secondary (community) sources.
- [ ] **Change-tracking workflow.** How do we notice when Claude Code's permissions/security surface changes? Options to evaluate: (a) GitHub releases watcher on anthropics/claude-code, (b) `claude.exe` byte-level diff between versions with auto-flag on the `XIq` / `h0` / `sI8` symbols + the relevant code regions, (c) `settings.json` schema diff against a pinned baseline, (d) probe-suite regression run on each new version, (e) RSS / atom feeds for release notes. Pick a primary signal + fallbacks. Define what triggers a re-investigation pass.
- [ ] **Verification + regression suite.** Plan for extending `app-src/js-probes/probe.js` (or adding peers) into a versioned probe suite that exercises documented + experimentally-derived behavior: path-globbed allow rules, path-globbed deny rules, `bypassPermissions` setMode gate, `additionalDirectories` scope check, Bash content matcher, Skill rules with content, MCP rules with parens-content. Each probe records claude.exe version + result. The suite is the executable spec — if Anthropic ships a fix, the suite tells us, not anecdote.
- [ ] **Cadence + automation surface.** Manual / per-release / weekly / monthly. Which Claude Code primitive (`/schedule` remote agent, `/loop`, external Windmill flow, manual command) runs the regression suite + change-detect. Probably aligns with FEAT-0001's cadence; reference rather than re-decide.
- [ ] **Learning roadmap.** Honest gap assessment — for each topic in the scope list, rate current knowledge (deep / moderate / shallow / none) and identify the next 1–3 things to investigate to lift the weakest areas. Prioritize by expected payoff (does this area generate user-facing bugs? does it touch the upstream-issue-triage workflow from FEAT-0001?).
- [ ] **Memory integration.** Define what gets written to the cross-session memory system vs the KB. Suggested split: memory = stable facts about *this user's setup* + procedural lessons (e.g., the PowerShell BOM gotcha); KB = facts about Claude Code itself (versioned, citation-backed). Cross-link convention between the two.
- [ ] **Outward-facing artifacts.** Should knowledge be shared back? Options: README enhancements as understanding deepens, blog posts / writeups, contributions to upstream docs (PRs against anthropics/claude-code docs), comments on issues per FEAT-0001's workflow. Decide policy and disclosure stance.
- [ ] **Tooling inventory.** What MCP servers / SDKs / subagents help (claude-api skill for API research, claude-code-guide subagent for tool/hook questions, web search for release-note hunting, stackagentic-gateway for project-pulse-style monitoring, supabase memory for cross-session continuity). Map each tool to which planning area it serves.
- [ ] **Reuse vs build.** Same posture as FEAT-0001 — bias toward reusing existing toolchain pieces (task-manager for task spawning, the existing probe pattern). Identify what's net-new.
- [ ] **Honest uncertainties.** Several questions don't have obvious right answers (KB location, change-detect cadence, sharing policy). Surface them explicitly in the plan rather than picking arbitrarily — they're better as user-decision points.
