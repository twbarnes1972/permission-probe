# FEAT-0003: Plan ethical red-team / security-research workflow + responsible-disclosure pipeline for Claude Code CLI

**Created:** 2026-05-18
**Status:** Open
**Priority:** Medium
**Category:** Feature

---

## Summary

Plan (not yet execute) a structured ethical-security-research workflow for the locally-installed Claude Code CLI, covering: scope/rules of engagement, threat modeling, lab setup, tooling, finding documentation, and — critically, *first* — researching Anthropic's accepted channel(s) for security reports and the rules-of-engagement they publish. The deliverable is a written plan. Any actual testing is downstream of plan approval and bound by the disclosure-channel research done as criterion #1.

**Hard constraints (apply to this task and to anything that follows from it):**

1. All testing happens only against the maintainer's own local installations of Claude Code. **Never** against Anthropic-hosted services, the Claude model API, or any system the maintainer does not own.
2. No findings are publicly disclosed (in this repo or elsewhere) before going through Anthropic's coordinated disclosure process and respecting their published timelines.
3. No weaponization of findings. POCs exist only to demonstrate a vulnerability for the report; they're not packaged for offensive use.
4. This task is authorized security research on the maintainer's own tooling, not adversarial activity against any party.

## User Story

As maintainer of `permission-probe` — which already surfaced a security-relevant defect via [ISSUE-0001](../closed/ISSUE-0001.md) (path-globbed deny rules silently no-op, so "Edit(/path/to/secrets/\*\*)" deny lists protect nothing) — I want to extend that depth-of-investigation discipline to *deliberately* hunt for security issues in Claude Code's permission/hook/settings/MCP surface, so that:

- Issues are found responsibly, with reproducible evidence, before adversaries find them.
- Findings flow through Anthropic's accepted channel with the rigor they need to act on (root cause + repro + suggested fix), the way ISSUE-0001's findings did.
- The local installations I use daily are hardened against the most plausible attack patterns (malicious MCP server, hostile workspace, settings poisoning, hook supply-chain).
- This work strengthens the relationship with Anthropic's team rather than antagonizing it.

## Background

- ISSUE-0001 was framed as a functional bug but had real security consequences: any user relying on `Edit(.../secrets/**)` denies for safety was unprotected. The same matcher reject affects `Skill(...)` and `mcp__server__tool(arg)` rules — a strictly broader security boundary failure than was originally flagged. That was found accidentally during functional investigation. Systematic hunting would likely find more.
- The Claude Code attack surface has grown rapidly: hooks (PreToolUse, PostToolUse, Notification, SubagentStop, etc., each executing arbitrary shell), MCP servers (network-fetched tool definitions running with caller's trust), Skills (markdown that becomes executable through interpretation), settings cascade (system/project/user/local — each a privilege boundary), the dangerously-skip-permissions gate. Each is a candidate for adversarial testing.
- Encoding/parsing edge cases also matter: the BOM regression I hit while updating `~/.claude/settings.json` mid-session is benign on its own but illustrates that file-format parsing is a real surface (whose tolerance for malformed JSON, control chars, BOMs, etc. is undocumented).
- Anthropic almost certainly publishes a vulnerability-disclosure channel and may run a formal bug-bounty program. We don't currently know the exact channel, scope rules, or safe-harbor language. Researching that is criterion #1 below — it gates everything else.

## Acceptance Criteria

- [ ] **Disclosure channel research (gating — do this first).** Find Anthropic's published security-report channel. Candidates to verify: `security@anthropic.com`, a `SECURITY.md` in `anthropics/claude-code`, a HackerOne / Bugcrowd program, the Anthropic Trust Center / Security page, a public bug-bounty policy. Capture:
  - The authoritative URL(s) and contact path(s).
  - Documented scope (what they accept reports on) and out-of-scope items.
  - Disclosure timeline expectations (their policy + the industry default for cases where they don't specify).
  - Any safe-harbor language for good-faith research.
  - PGP key / encrypted-submission requirements.
  - Acknowledgment / hall-of-fame policy if any (informs whether to publish post-disclosure).
- [ ] **Scope + rules of engagement.** Concrete in-scope list (local `claude.exe` and its config processing, locally-installed hook scripts and their stdin payloads, `settings.json` cascade behavior, MCP servers running locally on the maintainer's machine, the embedded JS bundle's permission/security logic) and explicit out-of-scope list (Anthropic-hosted API, claude.ai, anthropic.com, any system not owned by the maintainer, social engineering against Anthropic employees, denial-of-service testing). Adopt Anthropic's published scope if they have one; document any deltas with rationale.
- [ ] **Threat model.** Identify threat actors (malicious workspace cloned by a developer, malicious MCP server installed by a developer, compromised hook script via supply-chain, hostile project CLAUDE.md, prompt-injection-triggered tool misuse, settings.json poisoning by a sibling process), assets at risk (user filesystem outside intended scope, credentials in `~/.ssh`/`~/.aws`/`.env`, secrets exfiltrated via Bash, integrity of subsequent tool calls), and trust boundaries (cwd scope, additionalDirectories, the deny matcher, the bypass-mode gate, MCP server origin trust). Use STRIDE or similar but keep it grounded — concrete scenarios, not abstract categories.
- [ ] **Lab environment design.** Reproducible isolated testing setup: dedicated VM or isolated user account, pinned `claude.exe` version(s), clean profile per test, network egress controls (so a misbehaving test can't reach the internet), filesystem snapshots for rollback, logging configuration. Document the snapshot/restore procedure so a test that goes sideways doesn't pollute the main workstation.
- [ ] **Tooling inventory.** What helps: the existing disassembly methodology from INVESTIGATION.md, `probe.js`-style picomatch verification, hook-stdin fuzzers (mutation-based JSON, oversized payloads, malformed UTF-8/BOM, embedded control chars), settings.json mutation testing (precedence/shadowing edge cases), MCP-server mock that emits hostile tool definitions, prompt-injection corpus for testing tool-use safety. Decide build vs reuse per item.
- [ ] **Finding documentation template.** Format for a single finding: title, severity (CVSS v3.1 base + environmental), summary, prerequisites, reproduction steps, evidence (binary offsets, logs, screenshots), impact, suggested mitigation, version(s) tested, references. Same rigor as ISSUE-0001's INVESTIGATION.md.
- [ ] **Pre-disclosure storage.** Where do findings live *before* coordinated disclosure completes? **Not this public repo** — that would itself be a disclosure. Options to evaluate: a private repo, encrypted local files (age / gpg), a private branch with restricted visibility, an external password manager / secure note. Pick one with a clear rationale on durability, accessibility for the maintainer, and resistance to accidental publication.
- [ ] **Post-disclosure publication policy.** After Anthropic's timeline expires (or earlier with their written consent), what goes public? A writeup analogous to INVESTIGATION.md, the POC code, the timeline of communications, credit to Anthropic for fixing. What stays private (employee names, internal email threads, anything that doesn't add public value). Default: minimal-credit-to-self, maximum-clarity-on-fix, no drama.
- [ ] **Reporting workflow.** Step-by-step for "I think I found something" → "Anthropic has it" → "fix shipped / timeline expired" → "post-disclosure writeup." Includes when to consult a second opinion, how to escalate if Anthropic doesn't respond within their stated SLA, and the ethics of going public if no fix ships in a reasonable window.
- [ ] **Cadence + automation surface.** When do red-team passes happen? Per major Claude Code release? Quarterly? After observing specific upstream activity (e.g., a permission-related PR lands)? Share automation primitives with FEAT-0001 / FEAT-0002 where possible.
- [ ] **Ethical guardrails — explicit list.** Codify the hard constraints from the Summary plus: no testing against another user's installation even with consent unless they're a co-maintainer (avoid coercion / pressure complications); no publication of pre-disclosure findings on a "leak" path (e.g., a dev's hot take on social media); honor any reasonable request from Anthropic to delay or modify disclosure; if a finding implicates a third-party MCP server or community hook, follow standard coordinated-disclosure practice with *that* maintainer too.
- [ ] **Conflict-of-interest disclosure.** This repo's `NOTICE.md` has a standing license grant to Anthropic specifically for Claude Code inclusion. That's a non-financial relationship that's worth disclosing in any security report so the recipient understands the context. Decide phrasing.

## Implementation Notes

- **Use planning mode.** `ExitPlanMode` after drafting; no actual security testing in this task. The plan is the deliverable.
- **Disclosure-channel research is the gate.** Before any other criterion is "in progress," the disclosure-channel research (criterion #1) needs a concrete answer. We need to know the rules of engagement before drafting test recipes — the rules shape what's appropriate to look for, document, and store.
- **Output location.** Plan goes to `tasks/working_artifacts/FEAT-0003/PLAN.md`. Sub-artifacts (lab-setup doc, finding template, ethical-guardrails checklist) go alongside.
- **What this task does NOT authorize.** Nothing here authorizes testing against Anthropic-hosted services, against any system other than the maintainer's own installations, against other users (even with consent, unless co-maintainer), or pre-disclosure publication of any finding. The plan must reinforce these constraints, not relax them.
- **Cross-reference siblings.** [FEAT-0002](FEAT-0002.md)'s knowledge base and verification suite are natural inputs to this task's threat model and tooling inventory; [FEAT-0001](FEAT-0001.md)'s commenting workflow has zero overlap with security disclosure and should be kept separate (public commenting on a not-yet-disclosed finding would be a serious procedural error).
- **Be honest about effort and risk.** Real security work is slow, easy to get wrong, and has real reputational stakes. The plan should acknowledge that and bias toward "do a small thing well" over "ambitious program that flames out."
