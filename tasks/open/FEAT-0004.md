# FEAT-0004: Plan strategic expansion beyond Claude Code — permissions/access-control/identity contributions across an open-source portfolio

**Created:** 2026-05-18
**Status:** Open
**Priority:** Medium
**Category:** Feature

---

## Summary

Plan (not yet execute) a strategic broadening of this repo's contribution surface beyond `anthropics/claude-code` to a portfolio of open-source projects in our tech stack, specializing in **permissions, user access controls, and identity**. The work `permission-probe` exists for — disassembly-deep root-cause work on a single closed-source project — is a transferable skill; this task plans how to apply that skill across multiple upstreams without losing focus. Deliverable is a written plan covering scope criteria, project prioritization, contribution-mode menu, README/NOTICE.md refactor approach, capacity model, and explicit handoffs to FEAT-0001/0002/0003. Implementation (actual contributions, README rewrite) is downstream and gated on plan approval.

## User Story

As the maintainer of `permission-probe`, which today reads as a single-purpose tool for one Claude Code bug, I want a documented strategy for contributing permissions/access-control/identity expertise to a curated portfolio of open-source projects (initial candidates: Python, Traefik, PostgreSQL, Windmill, Supabase, Restic, Kafka, Pomerium, CoreDNS, FreeRADIUS, Apache Airflow, Firezone), so that:

- The deep expertise being planned in [FEAT-0002](FEAT-0002.md) and the disclosure pipeline planned in [FEAT-0003](FEAT-0003.md) generalize across upstreams rather than staying captive to a single vendor's bug.
- The issue-triage workflow planned in [FEAT-0001](FEAT-0001.md) has a clear policy for which *other* upstream trackers it can be pointed at.
- README and project identity reflect the actual scope (a permissions/identity contribution practice that includes — but isn't limited to — Claude Code), without abandoning the still-useful Claude Code workaround content.
- For closed-source tools we contribute to, there is a documented `NOTICE.md` policy so disclosure boundaries and IP attribution stay clean.

## Background

This repo started as a workaround for one Claude Code bug (see [ISSUE-0001](../closed/ISSUE-0001.md)). The investigation produced reusable methodology (binary disassembly, probe-suite verification, version-pinned offsets). That methodology applies to many projects beyond Claude Code — especially the permissions/identity space, where the cost of a silent matcher bug is high and the bug class recurs across products.

The current planning tasks (FEAT-0001 issue triage, FEAT-0002 expertise KB, FEAT-0003 disclosure pipeline) are all *parameterized over a single upstream* (anthropics/claude-code). Broadening the contribution scope changes the shape of each: triage cadence per-project, KB topic surface per-product, disclosure channel per-program. This plan decides which projects are worth that broadening and in what order.

The Claude Code workaround content (hook script, README permissions deep-dive) is not going away — it stays as the canonical reference for that specific bug class until upstream ships a fix. The README *framing* shifts so a first-time visitor understands the repo as a permissions/identity contribution practice, with the Claude Code work as the founding case study.

A subset of contributions will be to closed-source projects (vendor SDKs, commercial tools we use). For those, public methodology + private artifacts split per `NOTICE.md`.

## Acceptance Criteria

- [ ] **Specialization scope definition.** Concrete rules for what's "in scope" for permission-probe's portfolio. Suggested starter: authentication, authorization, RBAC/ABAC, identity federation, session management, token/secret handling, sandbox/isolation, ACL/permission matchers, SSO/OIDC/SAML, MFA, secrets management, audit logging, access-control settings/schema. Note explicit *out* of scope (e.g., general bug fixes, feature requests unrelated to access control, performance tuning) — even when those are valuable, they're not what this practice is for.
- [ ] **Project prioritization rubric.** Scoring criteria for ranking the initial 12-project list (and future candidates). Suggested dimensions: (a) is this project in *our* production tech stack? (we feel pain firsthand), (b) does it have a permissions/identity surface large enough to merit deep work? (c) is the project receptive (responsive maintainers, documented contribution path, security policy)? (d) does it have a paid bounty program? (cross-ref GTSK-0003) (e) is the codebase tractable for the kind of work we do (compiled? interpreted? size?). Output a scored ranking of the initial list.
- [ ] **Per-project quick-fit assessment of the initial list.** For each of Python, Traefik, PostgreSQL, Windmill, Supabase, Restic, Kafka, Pomerium, CoreDNS, FreeRADIUS, Apache Airflow, Firezone: one paragraph noting permissions/identity surface, contribution channel, license, bounty program (if any per GTSK-0003), and a tier assignment (Tier 1 = engage now, Tier 2 = watch, Tier 3 = defer/skip with reason). Bias toward shrinking the list — better four serious engagements than twelve shallow ones.
- [ ] **Contribution-mode menu.** What kinds of contributions does this practice make? Suggested set: (1) issue triage + cross-linking (FEAT-0001 generalized), (2) root-cause investigation (the disassembly/probe playbook), (3) responsible disclosure (FEAT-0003 generalized per-project), (4) docs PRs in the permissions section, (5) code PRs (test cases, repro fixtures, occasional fixes for verified bugs), (6) external writeups citing the project. Define which modes apply per-tier.
- [ ] **README refactor approach.** Outline (not yet rewrite) how the README should re-frame the project. Constraints: keep the Claude Code workaround content intact and discoverable, add a top-level framing that positions this as a permissions/identity practice with Claude Code as the founding case, link out to the per-project work as it materializes. Decide whether the refactor is a separate sub-task or part of the implementation phase of this plan.
- [ ] **NOTICE.md policy.** When this practice contributes to a closed-source tool (vendor SDK, commercial product), how is that recorded? Suggested rules: list closed-source projects + a one-line scope-of-engagement per entry, no leaked private content, link to public artifacts when they exist, no disclosure of unfixed-but-private vulnerabilities (those live in `permission-probe-research/` per FEAT-0003). Decide whether `NOTICE.md` is created now (as a stub) or only when first triggered.
- [ ] **Capacity + cadence model.** Honest assessment of how many concurrent project engagements one maintainer (plus AI assistance) can sustain. Define: maximum active Tier 1 projects at once, per-project minimum cadence (e.g., "if we engage a project, we commit to at least one substantive contribution per quarter or we drop it back to Tier 2"), rotation policy.
- [ ] **Handoffs to FEAT-0001 / FEAT-0002 / FEAT-0003.** Concrete decisions about what each of those plans needs to generalize:
  - FEAT-0001 (issue triage): does the registry get a `project` column? Does each engaged project get its own triage cadence?
  - FEAT-0002 (expertise KB): does the KB topic tree get project-namespaced? How does shared cross-project content (e.g., "matcher bug class") live alongside project-specific knowledge?
  - FEAT-0003 (disclosure pipeline): per-project disclosure channels — does each Tier 1 project get its own charter excerpt, or is the existing FEAT-0003 charter parameterized?
  - For each: state what changes, what stays the same, and whether the change is a follow-up edit to the existing plan or a new task.
- [ ] **Outward identity question.** Open question, not a decided answer: does this practice want an external landing page / portfolio site / dedicated GitHub org separate from the personal account? Pros (clearer scope, easier for upstream maintainers to vet, room for future collaborators), cons (overhead, vanity-org problem if work doesn't materialize). Surface the question; let the user decide later.
- [ ] **Relationship to bounty research (GTSK-0003).** The bounty-program data from GTSK-0003 feeds the prioritization rubric. Define the handshake: GTSK-0003 produces the data, FEAT-0004 prioritization references it, refresh cadence stays with GTSK-0003.
- [ ] **Honest uncertainties.** Several decisions don't have obvious right answers — likely candidates: how aggressive to be about README reframing (risk: signal abandonment of the Claude Code use case), whether to engage projects we *don't* use in production (risk: shallow contributions get rejected), how to handle a project where the maintainers turn out to be hostile or unresponsive (risk: wasted effort or public friction). Surface these explicitly rather than pretending the rubric makes them disappear.

## Implementation Notes

- **Use planning mode.** Enter planning mode before any setup work. Deliverable is a written plan document, not a partial implementation.
- **Output location.** Plan goes to `tasks/working_artifacts/FEAT-0004/PLAN.md` per [tasks/artifacts_convention.md](../artifacts_convention.md). Per-project quick-fit notes can live as one file per project under the same folder (e.g., `tasks/working_artifacts/FEAT-0004/projects/traefik.md`) if that's more navigable than a single mega-document.
- **Cross-reference FEAT-0001/2/3.** Each of those plans assumed a single upstream. Where this plan changes their shape, write *what changes* and *whether the change happens via amendment to the existing plan or as a follow-up task*. Don't silently rewrite their assumptions.
- **Do not begin implementation.** No README rewrite, no NOTICE.md creation, no per-project outreach during this task. Each accepted area spawns its own implementation task (e.g., `DOC-NNNN: refactor README per FEAT-0004 framing`, `DOC-NNNN: create NOTICE.md stub`, `FEAT-NNNN: engage Tier 1 project N`).
- **Be candid about the risk profile shift.** Going public as a "permissions/identity contribution practice" across 12 projects is a different reputational posture than "I wrote a workaround for one Claude Code bug." The plan should address that posture shift — what gets harder, what gets easier, what could go wrong.
- **Project list is a starting point, not a contract.** The initial 12 are a starting hypothesis. The prioritization rubric may drop several and the per-project assessment may surface candidates not on the list (e.g., OpenLDAP, Keycloak, Authelia, Caddy security plugins). Don't treat the list as closed.
