# FEAT-0001: Recurring upstream issue triage + root-cause registry + helpful commenting workflow

**Created:** 2026-05-18
**Status:** In Progress
**Priority:** Medium
**Category:** Feature

---

## Summary

Plan (not yet build) a recurring lightweight workflow for tracking, triaging, and helpfully commenting on open issues at [anthropics/claude-code](https://github.com/anthropics/claude-code/issues) that touch permissions, `settings.json`, hooks, allow/deny rules, or related matcher behavior. Output of this task is a written plan that answers "what tools, what cadence, what database, what comment style, what auth, what risk controls" — *not* the implemented workflow itself. Once the plan is reviewed and approved, follow-up tasks implement each piece.

## User Story

As the maintainer of `permission-probe` (with verified root-cause knowledge of at least two upstream permission bugs from ISSUE-0001), I want a recurring lightweight triage workflow so that:

- Users hitting these bugs find quicker, more accurate answers via cross-linked comments on their issues, instead of symptom-soup threads that go stale.
- The Anthropic Claude Code team gets verified reports with code-level root-cause analysis (not "this doesn't work" reports), making their triage cheaper and the fix path shorter.
- Our own task tracker (ISSUE-0001 today, more in the future) stays in sync with what's actually open upstream — so when a fix ships, we know to retest and deprecate the workaround.

## Background

ISSUE-0001 root-caused two distinct bugs (`XIq` matcher reject + `bypassPermissions` launch-time gate) via binary disassembly of `claude.exe` 2.1.143.a06, with empirical reproducers. That investigation is the source-of-truth for at least three open upstream threads (#36884, #57132, #15921). It's almost certain that:

- More open issues at anthropics/claude-code map to those same two root causes but are currently filed as separate symptoms.
- New issues will be filed over time as more users hit the same matcher bug under different scenarios.
- Some issues will reveal *novel* root causes worth investigating with the same disassembly methodology.

This task plans the workflow. The work itself (building tools, running cycles, posting comments) is downstream and gated on the plan.

## Acceptance Criteria

- [ ] **Scope definition.** Concrete rules for which upstream issues count as "in scope" — keyword list, label list, title patterns, recency window. Should distinguish "permission/settings/hooks" (in scope) from "general Claude Code bugs" (out of scope).
- [ ] **Fetch tooling choice.** Compare options (gh CLI, GitHub REST API, GitHub GraphQL, RSS, webhook-based push) and pick one with rationale. Note auth requirements (token vs OAuth) and rate-limit constraints.
- [ ] **Cadence + automation surface.** Decide daily / weekly / on-demand, and which Claude Code primitive runs it: `/schedule` (cron-mode remote agent), `/loop` (interval-based local), manual slash command, or external (Windmill, GitHub Action). Capture tradeoffs.
- [ ] **Registry schema + storage.** Field list per tracked issue (suggested starter: `gh_issue_number`, `title`, `url`, `opened_date`, `reporter`, `gh_status`, `our_task_id`, `mapped_root_cause_id`, `workaround_status`, `last_seen_date`, `last_comment_date`, `confidence_score`). Pick storage: markdown table in the repo, SQLite under working_artifacts, the available Supabase MCP, or a Windmill-backed data store. Justify the pick.
- [ ] **Root-cause mapping model.** Define how a tracked GitHub issue links to known root causes. Suggested schema: each root cause gets its own ID (e.g., `RC-XIQ-MATCHER`, `RC-BYPASS-GATE`) with one paragraph of summary + a pointer to the artifact that documents it. A GitHub issue can map to 0..N root causes (0 = novel/uninvestigated, 1 = known dup, N = compound).
- [ ] **Per-cycle workflow draft.** Step-by-step: fetch open issues in scope → diff against registry → for each new issue: classify (known root cause / novel / out of scope) → decide action (comment / open internal task / skip / escalate). For each *existing* tracked issue: refresh status, note any new activity, decide whether to re-comment.
- [ ] **Comment style guide.** Tone (factual, helpful, never preachy or snarky about Anthropic). Required components of a substantive comment (cross-link to root cause artifact, workaround pointer, acknowledgment of dev team's known constraints, what info would help them verify). What to NEVER post (speculation, scope creep, "this is a security issue!!1" alarmism, anything that reads as marketing for this repo).
- [ ] **Auth + credentials.** What auth surface (gh CLI device flow, fine-scoped PAT, OAuth app) — and where credentials live. Whether the workflow runs as the maintainer's identity or as a bot account.
- [ ] **Internal task spawning.** When a novel root cause is found, the workflow should open a new task in `tasks/open/` following existing conventions. Define ID assignment (next ISSUE-NNNN? Different prefix for upstream-imported issues?), template, and how it cross-links back to the upstream issue.
- [ ] **Rate + politeness limits.** Maximum comments-per-week, cooldown between comments on the same thread, opt-out signal recognition (if a maintainer says "we know, please stop commenting," registry flags that thread to not be commented on again).
- [ ] **Ethical + reputational guardrails.** The workflow is touching a public, Anthropic-controlled issue tracker on behalf of one identifiable user. Address: how to avoid the appearance of brigading, what disclosure (if any) the comments should include about AI assistance in drafting, how to handle disagreement with a maintainer's triage decision.
- [ ] **Cost + effort estimate.** Rough time-per-cycle (e.g., "20-30 min weekly to review the registry diff and approve/edit draft comments") and any API costs (Claude tokens to summarize/draft, gh API usage).
- [ ] **Reuse vs build assessment.** Identify what existing toolchain pieces can be reused (stackagentic-library task-manager for task spawning, gitea-integration for mirroring, etc.) vs what's net-new. Bias toward reuse.

## Implementation Notes

- **Use planning mode.** When this task is picked up, enter planning mode (`ExitPlanMode` after drafting) before any code/setup work. The deliverable is a plan document, not implementation.
- **Output location.** Write the plan to `tasks/working_artifacts/FEAT-0001/PLAN.md` per [tasks/artifacts_convention.md](../artifacts_convention.md). Sub-artifacts (a registry schema sample, a draft comment template, etc.) go alongside in the same folder.
- **Do not begin implementation in this task.** Each acceptance-criterion area, once planned, may spawn its own follow-up task (e.g., `INF-0001: build the issue-fetch script`, `FEAT-0002: register and wire the recurring schedule`, etc.). Keep this task scoped to planning.
- **Be honest about uncertainty.** Several criteria (especially the ethical/reputational guardrails and the rate-limit numbers) don't have obvious answers. Surface the open questions explicitly rather than picking a number arbitrarily.
